# Единая модель местоположения: реализация и проверка

Проверено 10 октября 2026 года, приложение `http://localhost:5080`.

## Изменения

В обоих сценариях обязательный `region` и необязательные `settlement`, `district`, максимум 120 символов каждое. Пробельный регион отклоняется, пустые уточнения превращаются в `null`. Москва и Санкт-Петербург вводятся как регион, населённый пункт можно не заполнять. У формы нарушения больше нет произвольного адреса вместо этих полей.

`LocationRequest`, `LocationDto`, `LocationMatchDto` задают общий контракт. `LocationMatcher` используется обоими существующими сервисами. Он выбирает первый непустой уровень внутри региона: регион + населённый пункт + район → регион + населённый пункт → регион + район → регион. Уровни с отсутствующими параметрами пропускаются. `match.level`, `match.isFallback` и `message` позволяют объяснить расширение поиска. Категория предмета и тип нарушения фильтруются до подбора местоположения. Общий ресурс организации добавляется отдельно; при отсутствии местных организаций остаются рекомендации из SQLite.

Gemini извлекает ту же тройку в канонической форме, не генерируя факты. При неизвестном регионе чат предлагает его уточнить, сохраняя остальные распознанные параметры для формы. Ручные поля не вызывают LLM. Готовый тип нарушения не вызывает LLM; распознавание описания продолжает работать.

Ключи `sessionStorage` оставлены прежними. Все три поля сохраняются при вводе и восстанавливаются при возврате/перезагрузке/навигации. Старый `city` переносится в регион только для Москвы/Санкт-Петербурга; другой город — в населённый пункт. Старый адрес нарушения сохраняется как `legacyLocation` и показывается возле новых полей. Описание нарушения и кеш его распознавания не теряются. Переход из чата обновляет только непустые параметры.

Миграция `20261009214005_UnifiedLocation` переименовывает City в Region, добавляет уточнения и индексы. Рабочая база обновлена без удаления старых записей. Проверено также применение начальной и новой миграций к отдельной SQLite с сохранением старых данных. SeedData создаёт новую базу самостоятельно и однократно дополняет прежнюю: всего 7 учебных пунктов и 24 записи организаций для четырёх типов. Новые региональные организации явно названы учебными и не имеют вымышленных сайтов.

## Реальный Gemini

- «Куда сдать батарейки в Москве?» и «Я из Москвы. Куда сдать батарейки?» → `find_disposal`, регион Москва, населённый пункт `null`.
- «Под Москвой хочу сдать батарейки. Где есть пункты?» → регион Москва после уточнения инструкции, согласно ранее согласованному поведению.
- «Куда сдать батарейки в Санкт-Петербурге, Петроградский район?» → регион Санкт-Петербург, населённый пункт `null`, район Петроградский.
- «Куда сдать батарейки в Ленинградской области, во Всеволожске, Всеволожский район?» → регион Ленинградская область, населённый пункт Всеволожск, район Всеволожский.
- «Куда сдать батарейки в Казани?» → регион `null`, населённый пункт Казань; чат просит регион.
- «В реку Москва в Коломне сливают грязную воду. Что делать?» → `environmental_violation`, регион `null`, населённый пункт Коломна; река не превращается в регион Москва.
- Через интерфейс чата пройдены оба сценария для Всеволожска: все три поля переданы в существующий черновик, после отправки формы показана соответствующая учебная запись из SQLite.
- Прежние четыре контрольных вопроса: батарейки → `find_disposal`; сжигание мусора → `environmental_violation`; раздел сообщения → `navigation`; «Как дела?» → `unknown`.

При первом прогоне новой инструкции Gemini вернул пустой регион для «под Москвой». В системную инструкцию добавлен явный пример нормализации, backend-правила склонения не добавлялись. После пересборки весь реальный прогон прошёл. Ошибок доступа, квоты или structured JSON при итоговых проверках не было.
