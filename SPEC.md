\# Экопомощник — спецификация MVP



\## 1. Назначение проекта



«Экопомощник» — учебное веб-приложение, которое помогает пользователю решать бытовые экологические задачи.



В рамках MVP реализуются три основных сценария:



1\. Поиск места, куда можно сдать отход или ненужную вещь.

2\. Получение рекомендаций при обнаружении экологического нарушения.

3\. Общение с тематическим AI-помощником.



Приложение запускается локально. Публикация в интернете и Docker на данном этапе не требуются.





\## 2. Технологический стек



Backend:

\- C#

\- ASP.NET Core Web API



Frontend:

\- обычный HTML

\- CSS

\- vanilla JavaScript

\- без React, Vue, Angular и других frontend-фреймворков

\- без Razor и .cshtml



Данные:

\- SQLite

\- Entity Framework Core



AI:

\- внешний LLM API

\- API-ключ хранится только на backend

\- провайдер LLM не должен быть жестко связан с frontend



Frontend должен располагаться в `wwwroot` и раздаваться самим ASP.NET-приложением.



Приложение должно запускаться как один локальный ASP.NET-проект.





\## 3. Общая архитектура



Browser

→ HTML/CSS/JavaScript

→ ASP.NET Core Web API

→ Services

→ SQLite / внешний LLM API



Frontend обращается к backend через `fetch` и получает JSON.



Frontend не должен напрямую обращаться к LLM API и не должен содержать API-ключ.





\## 4. Дизайн



В папке `design-reference/figma` находится прототип, созданный в Figma Make.



Его необходимо использовать как визуальную основу:

\- сохранить цветовую схему;

\- типографику;

\- расположение основных блоков;

\- навигацию;

\- внешний вид форм;

\- карточек;

\- футера;

\- состояний загрузки;

\- общий стиль страниц.



Код Figma не требуется переносить буквально.



Необходимо убрать ненужную техническую обвязку Figma/Vite и реализовать итоговый frontend на обычных HTML/CSS/JavaScript.



Если код прототипа и его внешний вид конфликтуют, ориентироваться на внешний вид и поведение прототипа.





\## 5. Основные страницы



\### Главная



Навигация:

\- Главная

\- Куда сдать

\- Сообщить о нарушении

\- AI-помощник



Главная кратко объясняет назначение сервиса и дает переходы к основным функциям.



\### Куда сдать



Пошаговый сценарий:



1\. Пользователь указывает предмет.

2\. Указывает город и необязательно район.

3\. Получает:

&#x20;  - рекомендации по подготовке предмета;

&#x20;  - подходящие пункты приема;

&#x20;  - адрес;

&#x20;  - режим работы;

&#x20;  - информацию о принимаемых категориях.



Должны поддерживаться:

\- переход назад между шагами;

\- сохранение введенных данных;

\- состояние загрузки;

\- состояние отсутствия результатов;

\- новый поиск.



\### Сообщить о нарушении



Пошаговый сценарий:



1\. Пользователь выбирает тип нарушения или описывает проблему.

2\. Указывает местоположение, если оно известно.

3\. Получает:

&#x20;  - рекомендации;

&#x20;  - что желательно зафиксировать;

&#x20;  - подходящую организацию или службу;

&#x20;  - ссылку/кнопку для получения информации об обращении.



Для MVP использовать несколько типов:

\- незаконная свалка;

\- сжигание мусора;

\- загрязнение водоема;

\- незаконная вырубка деревьев.



Если местоположение не указано, выводятся общие рекомендации.



Система сама не отправляет официальные обращения.



\### AI-помощник



Простой тематический чат-бот.



Пользователь пишет вопрос обычным языком.



Бот может:

\- дать короткую подсказку;

\- определить нужный раздел сайта;

\- показать кнопку перехода;

\- распознать параметры запроса;

\- при возможности передать распознанные параметры в соответствующий сценарий.



Примеры:



"Куда сдать батарейки в Москве?"

→ определить сценарий поиска места сдачи;

→ распознать предмет и город;

→ дать подсказку и кнопку «Куда сдать».



"Во дворе постоянно сжигают мусор. Что делать?"

→ определить сценарий экологического нарушения;

→ показать подходящую информацию и переход в раздел нарушений.



"Как дела?"

→ сообщить, что помощник работает только с вопросами по экологии и возможностям «Экопомощника».





\## 6. Ограничения AI



LLM не должна быть основным источником фактических данных.



Основная задача LLM:

\- определить намерение пользователя;

\- извлечь параметры из естественного языка;

\- определить, какой сценарий системы подходит.



Пример результата:



{

&#x20; "intent": "find\_disposal",

&#x20; "item": "батарейки",

&#x20; "city": "Москва",

&#x20; "district": null

}



Допустимые intent на первом этапе:



\- `find\_disposal`

\- `environmental\_violation`

\- `navigation`

\- `ecology\_help`

\- `unknown`



Фактические сведения о пунктах приема, нарушениях, организациях и рекомендациях необходимо получать из базы данных приложения.



LLM не должна:

\- придумывать организации;

\- придумывать ссылки;

\- придумывать пункты приема;

\- отвечать на посторонние темы;

\- самостоятельно создавать неизвестные системе действия.



Для неизвестного или постороннего запроса используется `unknown`.



Ответ пользователю при таком запросе:

«Я могу помочь только с вопросами об экологии и возможностях Экопомощника.»





\## 7. База данных



Для MVP достаточно следующих основных сущностей.



\### WasteCategory



\- Id

\- Name

\- PreparationInstructions



\### CollectionPoint



\- Id

\- Name

\- Address

\- City

\- District

\- WorkingHours

\- Website



\### CollectionPointWasteCategory



Связь пункта приема с принимаемыми категориями.



\### ViolationType



\- Id

\- Name

\- Recommendations

\- WhatToRecord



\### Organization



\- Id

\- Name

\- City

\- ViolationTypeId

\- Website

\- Description



На первом этапе база заполняется небольшим набором демонстрационных данных.





\## 8. Backend API



Примерный набор endpoint:



\### Поиск пунктов приема



GET `/api/recycling/search`



Параметры:

\- item

\- city

\- district



Возвращает рекомендации по подготовке и найденные пункты.



\### Рекомендации по нарушению



GET `/api/violations/recommendations`



Параметры:

\- type

\- location



Возвращает рекомендации и подходящие организации.



\### AI-помощник



POST `/api/chat`



Пример запроса:



{

&#x20; "message": "Куда сдать батарейки в Москве?"

}



Backend:

1\. отправляет текст в LLM;

2\. получает структурированный intent и параметры;

3\. проверяет результат;

4\. при необходимости получает данные из БД;

5\. формирует ответ для frontend.



Frontend не должен сам интерпретировать ответ LLM.

\## 10. Что не реализуем в MVP



Не требуется:

\- регистрация и авторизация;

\- личный кабинет;

\- админ-панель;

\- карта;

\- загрузка фотографий;

\- отправка официальных обращений;

\- история переписки;

\- голосовой ввод;

\- микросервисы;

\- Docker;

\- сложные внешние интеграции;

\- React;

\- Razor Pages/MVC Views.





\## 11. Требования к качеству



Код должен:

\- быть понятным для студенческого проекта;

\- не содержать лишней архитектурной сложности;

\- быть разделен на frontend, API, сервисы и работу с данными;

\- корректно обрабатывать ошибки;

\- не раскрывать API-ключ LLM;

\- не хранить секреты в Git;

\- иметь понятные имена классов и методов.



Не использовать сложные паттерны проектирования без необходимости.





\## 12. Критерии готовности MVP



MVP считается готовым, если:



1\. Приложение запускается локально.

2\. Все четыре основные страницы открываются и имеют единый дизайн.

3\. Сценарий «Куда сдать» получает данные через backend и SQLite.

4\. Сценарий экологического нарушения получает данные через backend и SQLite.

5\. AI-помощник реально обращается к внешнему LLM API.

6\. AI-помощник распознает хотя бы несколько типов запросов.

7\. Посторонние запросы корректно отклоняются.

8\. Кнопки из AI-помощника ведут только в существующие разделы.

9\. Реализованы состояния загрузки и отсутствия результата.

10\. API-ключ отсутствует во frontend-коде.
